# Рейсовый default, стационарный опыт и прогресс `/4`

## Пользовательский результат

Fresh `/4` для `sputnik-d` по умолчанию запускает **повторяемый шахтёрский рейс** на 3600 модельных секунд: станция → перелёт → добыча до заполнения трюма → обратный перелёт → разгрузка → следующий рейс. Расстояние до места добычи редактируется. Графики показывают повторяющиеся участки полёта, добычи и обслуживания; результат отдельно показывает добыто, доставлено, осталось на борту и число завершённых рейсов.

Прежняя однофазная модель не удаляется. Она становится явно выбираемым режимом **«Стационарная нагрузка»** для непрерывных и составных испытаний тепла, питания, прочности и сигнатур без cargo/flight.

Оба режима показывают живой прогресс и не заставляют UI перерисовываться после каждого модельного шага.

## Обнаруженное нарушение

- Старый Ship Fitting сохранил событийный рейс, cargo и редактируемое расстояние, но `/4` fresh-default создаёт одну фазу `work` на весь горизонт и не считает полёт, груз или доставку.
- `/4` также использует `60 с` вместо принятого fresh-default `3600 с`.
- Start/checkpoint передают Worker `maxSteps: 1`; после каждого шага UI полностью обновляет графики. Расчёт корректен, но длинный опыт неоправданно медленный и не имеет явного progress bar.
- Увеличить однофазный опыт до 3600 с недостаточно: это оставляет корабль под одной нагрузкой и не возвращает рейсовый пользовательский результат.

## Архитектурная граница

### Две версии работы, без скрытой подмены solver

- Существующий `ship-fitting-ship-model-0.1` остаётся буквальным stationary model. Старые run/result/checkpoint открываются и продолжаются без миграции.
- Для рейса вводится отдельный versioned model tag `ship-fitting-ship-model-mission-0.1` и mission-state. Он использует тот же `/4` energy/thermal/durability/signature kernel, а не V2 cast и не старый solver.
- Fresh workspace создаёт mission model. Переключатель «Тип работы» позволяет явно создать новый stationary draft; переключение не переписывает импортированный документ.

### Рейсовый controller

Рейсовый wrapper переносит уже принятую семантику `ship-fitting-v2.2-mission-brief` на `/4` kernel:

- реальные маршевые и тормозные запросы проходят через установленный roster;
- фактическая доступная тяга учитывает питание, топливо, температуру, остановки и профиль корпуса;
- масса в полёте равна dry mass + текущие запасы + фактическая масса руды;
- добыча получается из фактической полезной энергии лазеров через `LAB-ORE-01`; возврат тепла процесса остаётся отдельной долей энергетического баланса;
- разгрузка разрешена только после физического возврата и остановки у станции;
- температура, буфер, прочность, RNG и заряд не сбрасываются между рейсами; явно настроенное станционное пополнение сохраняет свою принятую endpoint-семантику;
- пока остаётся время и `repeat=true`, после обслуживания немедленно начинается следующий рейс — horizon не превращается в ожидание.

Параметры default берутся из текущего принятого mission owner: 3600 с, 100 км в одну сторону, полный трюм, цель 10000 SCU, подход 10 с, обслуживание 10 с, повтор включён. Это лабораторные условия, не новые ТТХ корабля.

### Данные и сохранение

Mission spec/state/result явно сохраняют process, route, onboard cargo, mined/delivered totals, completed trips, position, velocity, stage and stage clocks. Checkpoint содержит всё состояние, необходимое для совпадения следующего решения после reopen. Старые stationary и governor документы не получают синтетических mission-полей.

### Производительность и progress

- Fresh duration для mission и stationary — 3600 с; explicit/imported duration сохраняется буквально.
- Start/checkpoint ordinary и governor запрашивают до 2000 шагов на пакет. Существующий wall budget 80 ms остаётся верхней границей; Step остаётся одним шагом.
- Progress и графики читают один accepted Worker snapshot. Внизу видны elapsed/total/%; Pause/Cancel обрабатываются между пакетами.
- ETA не показывается.

## Видимый контракт

Mission mode показывает:

- тип работы и редактируемые расстояние, режим скорости, подход, обслуживание, цель и повтор;
- текущую стадию, позицию/скорость и cargo;
- добыто всего, доставлено, на борту, SCU/ч и завершённые рейсы;
- те же power/temperature/resource/signature graphs, дополненные position/velocity/cargo/delivered.

Stationary mode показывает существующий action/phase editor и actual `usefulWorkJ`; поля рейса и SCU не имитируются.

## Приёмка

1. Fresh `/4` открывается на `sputnik-d`, mission mode и 3600 с; расстояние доступно для редактирования.
2. За 3600 с контрольный Sputnik-D выполняет четыре полных возврата с разгрузкой. В trace различимы четыре рейсовых цикла; `mined = delivered + onboard`, каждое обслуживание сдаёт положительный груз, пустого ожидания до горизонта нет.
3. Изменение расстояния меняет реальное время/число рейсов, а не только подпись формы.
4. Mission использует `/4` kernel: fuel, charge, temperature, buffer, durability and signatures непрерывны; energy residual остаётся в допуске.
5. Переключение на stationary сохраняет однофазный/составной опыт без cargo/flight. Старые stationary документы открываются буквально.
6. Pause → export → import → checkpoint continuation совпадает с uninterrupted mission по следующей стадии, cargo, запасам, RNG и финальному результату.
7. Реальный fresh Sputnik-D 3600 завершается не более чем за 20 секунд на штатной CI-конфигурации, показывает промежуточный прогресс, живые изменения графиков, финальные 100% и пустую ошибку.
8. Governor batching/progress работает по ticks; его физика, synthetic qualification и runtime authorization не меняются.
9. Видимая версия Лабы повышена; прежний root Ship Fitting и его сохранённые результаты остаются совместимы.
