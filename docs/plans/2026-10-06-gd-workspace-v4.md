# Цель, текущее состояние и граница работы

Цель — удобный инструмент ГД с сохранённой цепочкой открытия, редактирования,
расчёта, анализа и сравнения. v3 работает технически, но изолирует области работы,
теряет контекст корабля/измеренной ревизии, затрудняет анализ каналов и восстановление
сохранённого исследования. WHAT и WF01–15 — в продуктовом документе v4.

Оператор2026-10-06 поручил исполнять план и добавить версию в футер. Повторное
согласование не требуется. Исполнение — по PM_ROLE3.0: один Developer для всей
связанной UI/state области, QA целых цепочек и один scoped Code Review. Типовой
SDD per-task reviewer swarm здесь не применяется; Beads заменяет отдельный task ledger.

Режим PRODUCT, Beads `ulab-bn1`, существующий Draft PR6. Один Developer; PM не
пишет runtime. Численное ядро, каталог, сценарные правила, Worker и существующие
форматы остаются источниками данных. Новые маршруты, добыча до заполнения,
заправка, обнаружение и рейтинг кораблей не входят. v1 и v2 — проверяемые источники
возможностей, а не разрешение смешать разные расчётные модели.

# Порядок реализации

1. **Восстановить общую рабочую страницу и контекст.** Переиспользовать текущие
   представления и один workspace, заменить скрытые экраны доступными секциями и
   якорями. Компактный паспорт, группы слотов и каталог сохраняют монтаж. Схема
   слотов раскрывается дополнительно. Видны выбранный корпус, черновик, активный
   опыт и измеренный результат; импортированный опыт показывает свои данные.
   Правки следующей сборки не меняют immutable расчёт. WF01–06, WF12.
   Футер показывает «интерфейс v4.0» на desktop и touch; версия модели остаётся
   отдельно. Не менять package/model/schema версии ради маркировки UI. WF15.
2. **Вернуть понятный анализ и сравнение.** Основные обзорные графики, стабильные
   цвета каналов, читаемые оси и пороги; полные каналы остаются исследовательскими
   подробностями. Выбор времени связывает график/таблицу/события. Сравнение показывает
   состав, корпус, измеренную ревизию, интервал и значения отличий; база не зависит
   от сортировки. Эталон доступен на паузе и не стирает текущий результат. WF07–12.
3. **Восстановить управление исследованием.** Показать поддерживаемые, но скрытые
   настройки начального состояния, заданных фаз и повтора. Расширение формы локальных
   ТТХ опирается на существующие поля, валидацию и experimental provenance;
   неподдерживаемые параметры не выдумываются как канон. Различить открытие сборки,
   опыта для повторения и результата для анализа; явно подписать состав экспортов
   и границы восстановления. WF01, WF03, WF06, WF13–14. Чтение сохранённого результата
   требует отдельной проверки его чисел/каналов/интервалов до показа; одного принятого
   RunSpec недостаточно для объявления восстановления измерений.

## Поверхность исполнения и Verification Contract

Текущие owners: `src/app/fitting.ts`, `fitting-workspace.ts`, `fitting.css`,
`fitting-ui/{ship-view,lab-view,lab-channels,compare-view,presentation,telemetry}.ts`,
`src/io/fitting-json.ts`. Уточнение IO допускается только для валидации/открытия
собственного result; существующие форматы, replay и numerical owners сохраняются.
Developer выбирает локальные helper-файлы по обязанности, без новой архитектуры
или зависимости. Старые тесты isolated screen/locked draft обновляются на новый
принятый WHAT; numerical/ownership assertions не удаляются ради зелёного результата.

Конкретные цепочки, error/edge/invariants и scoped Review Contract —
`docs/verification/gd-workspace-v4-contract.md`. Этапы связаны одним workspace:
этап1 производит постоянную identity и next draft, этап2 использует measured identity
и trace, этап3 открывает тот же проверенный snapshot. Поэтому один Developer
реализует весь scope, без промежуточных независимых per-task review launches.
Для всех трёх этапов: подходящий RED → GREEN на поведении → affected regression.

До кода: независимый Plan Review этого HOW и WF01–15 → `PLAN_READY`.
Текущее адверсальное ревью существующего UI не является этим вердиктом.

Developer владеет durable regression tests. Адресные проверки: цвет после toggle,
измеренная/черновая ревизии, независимость базы от sort, Freeze paused snapshot,
показ импортированного корпуса/условий, atomic отказ плохого файла. Затем QA
проверяет полные цепочки с настоящим Worker: открыть→изменить→запустить→перейти
к анализу→зафиксировать эталон→изменить→сравнить→экспортировать→повторно открыть.
Нужны desktop, plain LAN touch 390 и tablet 820; физический планшет отмечается
отдельно. Проверки элементов и старые технические PASS цепочку не заменяют.

Один scoped Code Review проверяет изменённые UI/state/import поверхности:
владение данными, недублирующиеся controls/DOM IDs, подписи измерений, чтение
невалидных результатов, сохранение источников и доступность действий во время
расчёта. После blocker fix — только affected QA и scoped re-review.

Обязательные project guards сохраняются. Численное evidence наследуется только
для неизменных owners; полный численный прогон не запускается ради раскладки.
После каждого третьего завершённого QA/Review+триаж — короткий самоаудит PM.
